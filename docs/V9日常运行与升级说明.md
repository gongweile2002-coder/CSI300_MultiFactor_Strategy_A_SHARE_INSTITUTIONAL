# V9 日常运行与升级说明

更新日期：2026-09-12。v9 继续使用既有核心因子和交易约束，重点解决真实运行时的数据一致性、旧信号误用及操作证据保留。真实委托默认关闭；没有连接你的账户或验证真实投资收益。

## 先做什么

按根目录 README 安装依赖，然后运行：

```bash
python live.py doctor
```

也可在安装完成后打开 `START_CHECK.command`（Mac）或 `START_CHECK.bat`（Windows）。检查报告在 `outputs/v9_doctor/doctor.md` 和 `doctor.json`。报告显示当前电脑的 Python、依赖、Token 是否存在、数据检查结果、真实下单开关和具体下一步；不显示 Token 值，也不会连接券商或发送委托。

Mac 可以运行数据核查、选股、计划和人工回报流程；MiniQMT 仍需券商支持的 Windows 环境。看到 `xtquant=false` 不意味着 Mac 上的数据分析不能使用。看到依赖或 Token 存在，也不代表已经验证远程权限、券商连接或策略业绩。

## 日常准备变成一条命令

在收盘数据完成后运行：

```bash
python live.py prepare --download
```

此命令显式联网下载完整数据，然后做跨表核查、生成信号并归档。`prepare` 不下单。已经下载完当日数据时，可以使用：

```bash
python live.py prepare --data data/live --output outputs/v8_signal
```

沿用 `outputs/v8_signal` 和 `ops/live_v8.sqlite3` 路径是为了兼容既有目录，不代表还在运行旧版。默认风险配置版本变为 `A_SHARE_V9_2026_09_12`，策略ID仍保持 `CSI300_CORE_V8`，防止软件升级绕开同日订单ID。

只检查数据、不生成信号：

```bash
python live.py audit --data data/live --output outputs/v9_audit
```

`check` 也使用新的数据核查，返回0只代表所检查的数据条件通过，**不代表实盘上线许可或策略有盈利能力**。缺少真实数据时返回2及BLOCK是预期行为。

## 新增检查究竟检查什么

| 环节 | v9 检查 |
|---|---|
| 文件完整性 | 11类必要数据文件和清单一致，逐文件SHA256匹配 |
| 日期 | 数据最新日期等于清单日期和最近完整交易日；市场行情不能出现在日历休市日 |
| 数据主键 | 行情、估值、成分、财务版本等不重复 |
| 价格和单位 | 原始价、复权因子、成交量和金额有效；价格关系正确；成交量为股、金额为元 |
| 研究价与交易价 | 原始价 × 复权因子与研究价逐行对应；两个文件主键、成交量额与 raw 副本一致 |
| 股票池 | 最新300只成分快照有效，历史并集数量与清单一致；当前行情与估值覆盖至少95% |
| 参考资料 | 历史成分没有遗漏证券资料，行业区间、财报日期关系与基准数据满足基本条件 |
| 信号 | 目标、参考资料、因子审计和信号报告属于同一次生成；配置未发生变化 |
| 账户 | 真实账户的风险基准日期必须等于前一交易日 |
| 归档 | 输入、信号、配置与计划相互对应；台账通过SQLite在线备份保留已提交的WAL记录 |

停牌股票在日线数据源中可能没有当日行情，缺少少数成分时会给出警示；超过阈值停止。阈值检查不能独立判断“真实停牌”还是“漏数”，还需查看证券状态。日期、行情单位和API语义依据见[交易规则与接口依据](交易规则与接口依据.md)，原始日线说明来自 [Tushare官方文档](https://tushare.pro/document/2?doc_id=27)。

## 信号不能再只拿一份CSV随意修改

生成成功后，信号目录新增 `signal_manifest_v9.json`。它记录信号日期、配置指纹、来源数据清单指纹及四个信号文件的指纹。以下情况会阻止 `plan`、`manual-register`、`qmt-snapshot` 或 `qmt-submit`：

- CSV 被手工修改、只复制了部分文件，或与另一版文件混用。
- 生成信号后改变了风控配置，却继续使用旧目标。
- 当前参考资料不是同一信号包的版本。
- 信号来自未来，或者不是本次交易日前一交易日。
- 上次生成中途失败，没有完整提交新信号清单。

复制信号时请复制整个目录，保留文件名 `targets.csv`。修改策略配置后重新运行 `prepare` 并重新复核计划。哈希用于发现意外改变和混用，不是数字签名，也不能证明供应商数据真实，更不能抵御拥有本机写权限的人重新生成全部哈希。

生成目录有并发锁。正常退出会清理锁；进程被强制终止时，残留锁会阻止后续生成。先确认没有运行进程，可以选择新的输出目录重新运行；不要在另一个仍在运行的生成进程旁边强删锁。

## 从 v8 升级时必须处理的两点

1. **保留原台账。** 使用原 `ops/live_v8.sqlite3`；不要换成空数据库、改策略ID或删除未知委托以重新下单。先查询并对账旧版遗留的活动委托。旧版回报仍可通过 `reconcile` / `qmt-reconcile` 处理。
2. **重新生成信号，更新真实账户日期。** 旧v8信号没有完整溯源清单，不能直接提交；账户 JSON 新增 `risk_reference_date`，必须填写前一交易日。MiniQMT会从你提供的风险参考文件自动带入。完整空值模板见 `config/account.example.json`，必须填真实数据后使用。

例如周一交易时，如果上周五开市，风险基准日期应为上周五，不能填周日。日期字段与昨收净资产、高水位必须来自同一更新流程，不能只改日期。已有个人配置可继续使用，但建议对照新版示例合并版本字段，再重新生成信号；保留真实费率和风险参数，不要无意覆盖为示例值。

## 自动归档与事后复查

`prepare`、`plan`、`manual-register`、`qmt-snapshot`、`qmt-submit` 和两种 `reconcile` 会在 `ops/archive` 下创建独立目录。公共参数 `--archive-root` 可更改位置，必须放在子命令前：

```bash
python live.py --archive-root D:/QuantArchive prepare
```

每次目录名称包含时间、操作种类和随机标识，不会覆盖上一批结果。准备阶段复制完整数据、信号和配置；计划阶段保存账户、行情、目标、计划与台账。QMT提交还保存批次开始前的账户和行情，以及重新核验后的计划；这些不是每个成交瞬间的完整逐笔盘口录像。对账阶段保存累计回报文件（人工路径）及台账；QMT回报写入台账。

核对某次归档是否完整：

```bash
python live.py archive-verify --directory ops/archive/实际目录名称
```

归档采用 SQLite `backup` 接口获取一致的已提交状态，避免只复制主数据库而遗漏WAL中的最新委托。可检验的是文件一致性和内部对应关系，不是外部审计认证。归档会占用磁盘，尤其是每次完整市场数据快照；请根据容量备份到自己的可靠存储，本版不自动删除旧证据。

若委托已经登记或发出，而后续归档失败，**不能把整个操作简单重跑**。先查看 `ledger` 和券商状态，委托状态仍以台账及券商回报为准，修复归档问题后继续对账。
